# v0.3 Alignment Review — `@designlasagna/schemas` ↔ `ds-language-server`

**Date:** 2026-07-09
**Scope:** All v0.2/v0.3 schema fields traced end-to-end through LSP types → parsers → providers.
**Related:** `../schemas/rfcs/0001-v0.3-schema-improvements.md` in the schemas repo.

The schemas repo shipped v0.3 (RFC-0001: open lifecycle vocab, conditions, collections,
manifest `extends`, composite values, a new **icons** manifest, `variantPatterns`, docs
links, `priority`/`keywords`) but the LSP was built against the v0.2 era. This review lists
every misalignment found while reading both projects, prioritized.

## Legend

| Level | Meaning |
|-------|---------|
| 🔴 P0 | Broken feature the *existing* (v0.2) schema already promises — a bug, not a missing feature |
| 🟠 P1 | v0.3 capability the LSP cannot consume |
| 🟡 P2 | Repo / docs / publishing hygiene |

---

## 🔴 P0 — broken against the schema as it exists today

These bugs exist for v0.2 *and* v0.3 manifests. None are caught by tests (see P2 #14).

### 1. Utilities: LSP reads `relatedTokens`, schema defines `tokens`

- Every schema version defines the related-tokens field on a utility class as **`tokens: string[]`**.
- The LSP model/parser uses **`relatedTokens`**, a field no schema version defines.
- Net effect: the "Related tokens" sections in hover and completion
  (`src/providers/hover.ts:134`, `src/providers/completion.ts:415`) are **dead code** for every
  schema-compliant manifest.

Affected: `src/types.ts` (`DSUtilityClass.relatedTokens`), `src/parsers/utilities.ts`,
`src/providers/hover.ts`, `src/providers/completion.ts`.

Fix: parser accepts `tokens` (and can keep reading `relatedTokens` defensively); type rename is
internal and safe.

### 2. Utilities: structured `deprecated` object is not parsed

The schemas' `Deprecated` shape is `{ message, removal, replacement }`. The utilities parser's
`parseDeprecated` only handles `boolean | string`, and separately reads top-level
`deprecationMessage` / `removal` / `replacement` fields **that no schema defines**.

For a schema-compliant manifest the result is:

- `isDeprecated: true` (object is truthy) ✓
- `deprecationMessage`, `removal`, `replacement` all lost ✗

Consequences:

- No time-aware diagnostic severity (`src/lifecycle.ts` `getDeprecationSeverity` always gets
  `undefined` removal → falls back to Warning).
- No "Replace with …" suggestion in hover/diagnostics (`buildDeprecationMessage` gets nothing).
- No quick-fix code action (code-actions read `data.replacement`, which is always undefined).

Contrast: the tokens parser **does** handle the structured object correctly — the utilities
parser simply never got the same treatment.

### 3. CEM: `replacement` is never wired through components / attributes

`replacement` exists in both `v0.2/cem-extensions.json` and `v0.3/cem-extensions.json`. The CEM
parser only populates it for `cssProperties` and `deprecatedValues`. `DSComponent` and
`DSAttribute` extend `LifecycleInfo` (which declares `replacement`) and the diagnostics +
code-actions providers both read `component.replacement` / `attr.replacement` — **but it is
always `undefined`**, so:

- No quick-fix for deprecated components or attributes.
- `buildDeprecationMessage` never renders a replacement for them.

Only `deprecatedValues` on attributes (e.g. `size="large"` → deprecated value) currently produce
working quick fixes. The rest of the pipeline (type → diagnostics → code-actions) is in place;
only the parser never sets the value.

## 🟠 P1 — v0.3 capabilities the LSP cannot consume

### 4. Flat `utilities` root array (RFC A3 `oneOf`)

v0.3 `utilities.json` allows a manifest root of `{ utilities: [...] }` (flat list) *or*
`{ categories: [...] }`. The parser reads `categories` (or a top-level raw array) only. A v0.3
manifest using the flat shape yields **zero utilities** silently.

### 5. Status vocabulary mismatch

| | LSP | v0.3 schema |
|---|-----|-------------|
| Closed set | `draft \| beta \| ready \| deprecated` | open |
| v0.3 CEM common values | — | `draft`, `experimental`, `beta`, `rc`, `stable`, `deprecated`, `removed` |
| v0.3 tokens `status` | — | any non-empty string |

Consequences:

- `stable` / `experimental` / `rc` / `removed` are dropped (`parseStatus` in `cem.ts` returns
  `undefined` for anything outside the closed set; same in the tokens parser).
- `removed` is not treated as non-recommended anywhere.
- `statusEmoji()` (`src/lifecycle.ts`) has no cases for the v0.3 terms.

Fix direction: make `Status` an open string, keep a known-value table for emoji/severity
defaults, and treat `{deprecated, removed}` as the "not recommended" set.

### 6. New **icons** manifest type (v0.3 only)

v0.3 introduces `icons.json` (definitions: `Icon`, `PlatformIcon`, `Deprecated`,
`DesignSystemMeta`, `Docs`). The LSP has:

- no `icons` entry in `ManifestSources` / `DSConfig.sources`,
- no discovery hook, no parser, no provider.

If icon-name completion / deprecation diagnostics are in scope for the LSP, this is a net-new
surface. (Recommend: defer to a follow-up ticket; at minimum document the gap.)

### 7. Token manifest `extends` not resolved

v0.3 `tokens.json`: `"extends": { type: "array" }` — *other manifests that should be loaded
alongside this one*. The store/discovery layer never follows it. A design system that splits
primitives into separate manifests (the RFC's stated motivation) will surface incomplete
tokens.

### 8. `resolved` values can be numbers or composite objects

v0.3 `ConditionValue = string | number | ConditionValue[] | { string: ConditionValue }`
(primitive, numeric, and composite/derived values — RFC C1). `DSToken.resolved` is typed
`Record<string, string>` and `value: string`. A composite or numeric token would render as
`[object Object]` in hover/completion snippets. Need a value formatter (JSON-pretty for
objects, direct for numbers).

### 9. `tier` / `collection` parsed but discarded

`AcmeTokenEntry` in the tokens parser declares `tier?: 'primitive' | 'semantic' | 'component'`
and reads `collection`, but neither is emitted on `DSToken`. No provider can use them. The token
model needs the fields and at minimum hover should show them.

### 10. Unused v0.3 (some v0.2) signals the LSP could surface

| Schema field | Since | LSP opportunity |
|---|---|---|
| `keywords: string[]` | v0.3 utilities | match in completion trigger / filter; show in hover |
| `priority: number` (lower = more important) | v0.3 utilities | sort completion items |
| `docs.url` / `docs.figma` / `docs.storybook` | v0.3 | links in hover (tokens, utilities) |
| `variants` + `variantPatterns` | v0.3 utilities | offer `class` completions for variants instead of only base names |
| `properties`, `platforms.web.className` | v0.3 utilities | hover: show generated CSS / platform note (`web only`) |
| `a11y: { contrast, warning }` | v0.2 **and** v0.3 (tokens, utilities) | a11y warning line in hover; possible diagnostic |
| `aliases: "all" \| string[]` | v0.3 tokens | hover: alias relationship |

None are blockers, but several (a11y, docs, priority) are cheap wins once the parsers are
rebuilt for P0.

### 11. Slots have no lifecycle

`cem-extensions` (v0.2 *and* v0.3) adds slot deprecation (`SlotExtensions`). `DSSlot` in the
LSP is `name + description` only, and diagnostics never scan slots. A deprecated
`slot="legacy"` is invisible to the language server.

## 🟡 P2 — repo / publishing hygiene

### 12. v0.3 is not published from `@designlasagna/schemas`

`schemas/package.json` is still `"version": "0.2.0"` with `files: ["v0.2"]` and
`exports` only mapping `./v0.2/*`. The `v0.3/` directory and RFC exist in the repo but no
semver tag / package export exposes them. Consumers validating against v0.3 via the npm
package cannot.

### 13. Docs are internally inconsistent

- LSP `README.md` only documents v0.2 `$schema` URLs
  (`https://designlasagna.recipes/v0.2/*.json`) — fine for v0.2, but says nothing about v0.3.
- LSP `docs/schema-design.md`:
  - the "Parsed tokens manifest schema (**v0.3.0**)" example uses the **v0.2** `$schema` URL
    and the old `cssVariable` top-level shape (deprecated-in-v0.3, in favor of `platforms.web.reference`);
  - the utilities proposal is labeled `schemaVersion: "1.0.0"` — inconsistent with the actual
    v0.3 `utilities.json`.
- LSP `package.json` is `0.1.0` with no v0.3 mention.

### 14. No v0.3 test coverage

Test fixtures (`test/fixtures/tokens.json`, `test/fixtures/utilities.manifest.json`) are v0.2
shaped. There is no fixture exercising: structured `deprecated`, flat `utilities`, `tier`,
`collection`, `keywords`, `priority`, `variants`, composite `resolved` values, or `extends`.
Every P0/P1 gap above is therefore invisible to the test suite.

## Suggested implementation order

Ordered by risk/complexity and dependency:

1. **Add v0.3 fixtures + tests** (tokens, utilities flat + categorized, structured deprecated)
   so steps 2–5 are regression-guarded.
2. **Utilities parser** (P0 #1, #2; P1 #4): accept `tokens`, parse structured `deprecated`,
   support flat `utilities` root. Emit `keywords`/`priority`/`docs` while we're here (P1 #10).
3. **CEM parser** (P0 #3; P1 #5, #11): wire `replacement` through components/attributes, open
   status vocabulary (+ `statusEmoji`, `isDeprecated` for `removed`), slot deprecation.
4. **Tokens parser + model + store** (P1 #7, #8, #9): safe `ConditionValue` rendering,
   `tier`/`collection`/`aliases` on `DSToken`, resolve manifest `extends`.
5. **Provider polish** (P1 #10): docs links in hover, keyword/priority completion sorting,
   variant completions, `a11y` warnings.
6. **Icons** (P1 #6, deferred): discovery `sources.icons`, parser, minimal
   completion/diagnostics provider.
7. **Schema repo** (P2 #12): v0.3 exports + version bump (`0.3.0` or `1.0.0` per team policy);
   tag release.
8. **Docs** (P2 #13, #14): align LSP README + `docs/schema-design.md` with the shipped v0.3.

## Open questions

- Is "icons in the LSP" in scope for v0.3, or a v0.4/follow-up?
- Should the LSP emit **new** diagnostics for `a11y` warnings, or hover-only?
- Status: keep accepting the old `ready` value, or treat it as unknown-but-non-deprecated?
  (Recommend: accept, map to `stable`-equivalent display.)
- Schemas repo: publish v0.3 as `0.3.0`, or was the RFC implying v0.3 = breaking so `1.0.0`?
